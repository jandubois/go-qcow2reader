## Executive Summary

PR 76 adds a generic `image.SnapshotReader`, a qcow2 snapshot-table parser, a
`snapshot` CLI subcommand, and a CI comparison against qemu-img. Well-formed
images list correctly, and CI passes. Three Important problems need small
fixes. An image whose data the reader cannot decode reports no snapshots and no
error (I1). A crafted table offset panics `Open` (I2). A script comment and the
commit message misdescribe the CLI and the API (I3).

Four reviewers ran against `b265ff4`, and all four finished on the first
attempt. I checked every finding against the code. Each Important finding has a

I1. **`Snapshots()` returns an empty list and no error when the image data is unreadable** — `image/qcow2/qcow2.go:591-597` [Codex GPT 5.6 Sol, Claude Opus 5]


The load is inside `if img.errUnreadable == nil` (line 570).

`Header.Readable()` rejects encrypted images (line 320), unknown incompatible
features (line 336), and compression types with no registered decompressor
(line 342).

For those images `SnapshotEntries` and `errSnapshots` stay nil, so
`Snapshots()` (line 706) returns `[]` with a nil error. The library registers
only zlib by default, so a caller that never calls `SetDecompressor` gets no
snapshots from any zstd image. Claude saw the example CLI print `[]` for a LUKS
image that `qemu-img info` lists with one snapshot. Reading the snapshot table
needs no decompression or decryption, so the table does not need the gate. In
the reproducer the zlib image is the control; only the compression type
differs.

I2. **A snapshot table offset of 2^63 or more panics `Open`, and the table has no size cap** — `image/qcow2/snapshot.go:68` [Gemini 3.1 Pro, Claude Opus 5]

```go
	r := io.NewSectionReader(ra, int64(offset), -1)
```

At 2^63 or more, `int64(offset)` is negative. `NewSectionReader` treats
`n = -1` as unbounded by setting its limit to `MaxInt64`, so `Read` computes
`limit - off`, which overflows to a negative length and slices `p[0:-6]`.
`Open` loads snapshots eagerly, so any caller that opens such an image crashes,
even one that only reads data. The merge-base has no snapshot parsing, so this
is new.

The unbounded reader also lets a table grow to about 8.7 GB (65,536 entries of
up to 132,136 bytes, computed), where QEMU rejects anything over 64 MiB
(`QCOW_MAX_SNAPSHOTS_SIZE`, checked in `block/qcow2-snapshot.c`). Claude
measured 1.33 GB peak RSS for a 1-byte `read` of an image with a 1 GiB table.
The 2^62 offset and the 1023-entry table are the controls.

```go repro

package qcow2_test

import (
	"bytes"
	"encoding/binary"
	"testing"

	"github.com/lima-vm/go-qcow2reader/image/qcow2"
)

// craft returns a v3 qcow2 header with a one-entry L1 table and the given
// snapshot fields, padded to 4 KiB and followed by table.
func craft(nbSnapshots uint32, snapshotsOffset uint64, table []byte) []byte {
	buf := make([]byte, 4096, 4096+len(table))
	copy(buf[0:4], qcow2.Magic)
	binary.BigEndian.PutUint32(buf[4:8], 3)       // version
	binary.BigEndian.PutUint32(buf[20:24], 16)    // cluster bits
	binary.BigEndian.PutUint64(buf[24:32], 65536) // virtual size
	binary.BigEndian.PutUint32(buf[36:40], 1)     // L1 size
	binary.BigEndian.PutUint64(buf[40:48], 512)   // L1 table offset
	binary.BigEndian.PutUint32(buf[60:64], nbSnapshots)
	binary.BigEndian.PutUint64(buf[64:72], snapshotsOffset)
	binary.BigEndian.PutUint32(buf[100:104], 104) // header length
	return append(buf, table...)
}
```

## Design Observations

### Concerns

- **The qcow2-specific result has no error path** (in-scope) [Codex GPT 5.6 Sol, Claude Opus 5].
  The `Snapshots()` doc comment (`image/qcow2/qcow2.go:703-705`) sends qcow2
  callers to the exported `SnapshotEntries` field, which is nil when the table
  failed to load, while the error is in the unexported `errSnapshots` (line
  539). Such a caller cannot tell a broken table from an image without
  snapshots. A method returning `([]qcow2.Snapshot, error)` over unexported
  storage would keep the result and the error together.
- **Eager parsing ties every command to the table's health** (future) [Claude Opus 5].
  With `nb_snapshots` set to 1 and a zero offset, I confirmed that `read` now
  prints `WARNING: Failed to read snapshots: invalid snapshot table offset: 0`,
  and `snapshot` prints the same error twice, as a WARNING from `Open` and again
  as an ERROR. Parsing on the first `Snapshots()` call through `sync.Once` would
  spare callers that only read data, at the cost of `SnapshotEntries` no longer
  being a plain field.
- **`readL1Table` has no size cap either** (future) [Claude Opus 5]. It
  allocates `L1Size` entries straight from the header
  (`image/qcow2/qcow2.go:454`), where QEMU refuses an active L1 table over
  32 MiB (`QCOW_MAX_L1_SIZE` in `block/qcow2.h`). This predates the PR; a cap
  there would follow the same pattern as I2's fix.
- **The example commands close the image file twice** (future) [Gemini 3.1 Pro, Gemini 3.5 Flash].
  Each command defers `f.Close()` and then `img.Close()`, which closes the same
  `*os.File`, and both errors are ignored (`convert.go:58`, `info.go:46`,
  `map.go:51`, `read.go:56` and `snapshot.go:51` in
  `cmd/go-qcow2reader-example/`). The new command follows its siblings, so a
  change belongs in one pass over all five, and a reviewer should not ask this
  PR to diverge from them.

### Strengths

- **An optional interface** (in-scope) [Claude Opus 5, Codex GPT 5.6 Sol].
  `image.SnapshotReader`, checked at compile time
  (`image/qcow2/snapshot.go:14`), adds the capability without changing
  `image.Image`, so other backends and existing callers are unaffected.
- **CI checks copy-on-write reads** (in-scope) [Claude Opus 5, Gemini 3.1 Pro, Gemini 3.5 Flash].

## Review Process Notes

**Skill improvements**

- **Header fields that place or size a read.** When a change parses a binary
  format from input it did not produce (a disk image, an archive, a network
  frame), follow every header field that becomes an offset, a length or a
  count through each type conversion, multiplication and allocation. Flag an
  unsigned field converted to a signed type with no range check, a count
  multiplied in a narrower type, and an allocation sized from a field before
  the bytes behind it are read. When the code cites a reference
  implementation's limits, read that implementation's validation of the same
  structure and list every limit it enforces, because a port that copies some
  limits usually drops others.
- **New work inside an existing guard.** When a change adds loading or
  computation inside an existing guard block (`if readable`, `if enabled`,
  `if err == nil`), ask whether the new work needs the guard's condition.
  Enumerate the inputs the guard excludes and check what the new accessor
  returns for each. A guard the feature does not need switches it off for
  those inputs, and an accessor that then returns an empty result with no
  error gives callers a wrong answer they cannot tell from a real one.

**Repo context updates**

- **`Open` gates loading on `Header.Readable()`.** `qcow2.Open` loads the
  header extensions, the L1 table, the decompressor and the backing file only
  when `Header.Readable()` passes, and that check rejects encrypted images,
  unknown incompatible feature bits and compression types with no registered
  decompressor. The library registers only zlib, so a zstd image is unreadable
  to a caller that never calls `qcow2.SetDecompressor`, while the example CLI
  registers zstd and reads it. When a change adds metadata loading to `Open`,
  check whether the metadata needs decompression or decryption. Metadata that
  needs neither but loads inside the gate comes back empty for those images,
  and a test that goes through the CLI cannot show it.
- **`io.NewSectionReader(ra, off, -1)` needs a non-negative offset.** The
  qcow2 reader uses `-1` as its idiom for an unbounded section (the header and
  the header extensions). With a negative `off`, the first `Read` computes a
  negative length and panics, and converting a `uint64` header offset at or
  above 2^63 to `int64` produces exactly that. Flag the idiom wherever the
  offset comes from a header field, and bound the reader or range-check the
  offset.
- **Severity baseline for hostile headers.** The qcow2 reader does not enforce
  QEMU's size caps. `readL1Table`, for one, sizes its allocation from the
  header's L1 size unchecked. Rate a new unbounded allocation from a header
  field as a Suggestion against that baseline, and a panic reachable from
  `Open` as Important, since it crashes callers that only read data.

### Design Observations

**Concerns**

- (future) Parsing the table eagerly in `Open` ties every consumer to the table's health. I set `nb_snapshots=1` with offset 0 and ran two commands:

### Executive Summary
This PR introduces support for reading internal snapshots from qcow2 images, effectively matching the `qemu-img snapshot --list` functionality for API consumption. The design is elegant and highly resilient to partial corruption, but contains a critical `int64` overflow vulnerability in the offset calculation that allows a maliciously crafted image to crash the parser via a slice bounds panic.

### Critical Issues

C1. **Panic on crafted qcow2 image with large SnapshotsOffset** — `image/qcow2/snapshot.go:68` (critical, regression)

```go
	r := io.NewSectionReader(ra, int64(offset), -1)
```

`SnapshotsOffset` is read from the QCOW2 header as an unchecked `uint64`. If a maliciously crafted image declares an offset greater than `math.MaxInt64` (e.g., `1<<63 + 5`), the `int64(offset)` cast evaluates to a negative value.

When `io.NewSectionReader` receives a negative offset alongside `n = -1`, its internal limit fallback logic sets the boundary to `math.MaxInt64`. When `binary.Read` subsequently triggers `SectionReader.Read`, the internal length calculation `limit - s.off` overflows, yielding a negative length. This instantly triggers a slice bounds out of range panic (`p[0:max]`), causing a denial of service (DoS) for any application parsing the disk image.

```go repro
func TestReadSnapshotsOffsetPanic(t *testing.T) {
	header := make([]byte, 104)
	binary.BigEndian.PutUint32(header[0:4], 0x514649fb)  // magic
	binary.BigEndian.PutUint32(header[4:8], 3)           // version
	binary.BigEndian.PutUint32(header[20:24], 16)        // cluster bits
	binary.BigEndian.PutUint64(header[24:32], 1024)      // size
	binary.BigEndian.PutUint32(header[60:64], 1)         // nb snapshots
	binary.BigEndian.PutUint64(header[64:72], 1<<63 + 5) // snapshots offset

	// This panics with "slice bounds out of range [:-6]"
	qcow2.Open(bytes.NewReader(header), nil)
}
```

Fix: Add a bounds check against `math.MaxInt64` before instantiating the reader.

```diff
 	if entries > maxSnapshots {
 		return nil, fmt.Errorf("too many snapshots (%d entries > %d entries)", entries, maxSnapshots)
 	}
+	if offset > math.MaxInt64 {
+		return nil, errors.New("invalid snapshot table offset: too large")
+	}
 	r := io.NewSectionReader(ra, int64(offset), -1)
 	snapshots := make([]Snapshot, entries)
```

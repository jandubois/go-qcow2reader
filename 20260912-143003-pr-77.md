## Executive Summary

PR 77 adds a dynamic VHDX writer and a `convert -O vhdx` option. The encoding
holds up: qemu-img reads the output back identical to the source, CI passes at
the review SHA, and a reviewer booted a converted image under Windows HCS. Five
Important findings remain. The README example finalizes a failed conversion,
invalid conversion options still destroy an existing target, two writer paths
have no test, and two comments misstate hole behavior and the BAT size.

Four reviewers ran against `65fefc6`. Codex's first launch failed on an expired
login and ran again after re-authentication. Every finding below was checked
against the code, and each Important one carries a reproducer run from this
report at the review SHA, with its fix applied and the reproducer run again.
Copilot's two comments on an earlier revision are both resolved here: the CLI
validates the output format and block size before `os.Create`, and the
`Writer` doc says a block is never deallocated.

## Important Issues

I1. **The README example finalizes a failed conversion as a valid VHDX** — `README.md:25-26` [Codex GPT 5.6 Sol]

```go
_ = convert.Convert(w, img, convert.Options{})
_ = w.Close()
```

The example discards the conversion error and calls `Close` anyway. `Close`
writes the BAT and then the file type identifier (`image/vhdx/writer.go:452-454`),
and writing the identifier last is what keeps an interrupted conversion from
being detected as a VHDX. Code that follows the example turns a failed
conversion into an image qemu-img opens without complaint, with the unconverted
half reading as zeros. The README's first example also drops errors, but there
a missed error ends in a nil-pointer panic; here it ends in a quietly wrong disk.


```go

// (as [os.File] does), the file is extended by truncation when blocks are
// allocated, so that the unwritten parts of the file remain holes on file
// systems supporting sparse files, including those that do not create holes
// for writes beyond the end of the file (e.g. APFS).
```

On APFS a write past EOF leaves the same hole `ftruncate` does, and neither
keeps a small gap: the probe allocates gaps of 16 MiB or less in full at fsync
and leaves gaps of 32 MiB or more as holes, identically in both modes. In a run
through the writer itself, a 10 GiB disk with 4 KiB written every 16 MiB gave a
644 MiB file with 512 MiB allocated with `Truncate` and 511 MiB without. The
comments at lines 293-294 and 403-404 and the commit message ("Unwritten parts
of the file are kept as holes by extending the file with Truncate") make the
same claim. Not measured on Linux or NTFS.

S2. **Converting a file onto itself destroys the source** — `cmd/go-qcow2reader-example/convert.go:91` [Codex GPT 5.6 Sol]

```go
	t, err := os.Create(target)
```

When the target names the source file (the same path, a symlink or a hard
link), `os.Create` truncates the source before `Convert` reads it. Run on a
64 MiB qcow2, `-O vhdx` fails part way and leaves a 4 MiB file behind; raw
output reports 100% and no error, and leaves a 64 MiB raw file where the qcow2
was. The raw path did this before the PR, and this PR does not change it.

Fix: open the target without `O_TRUNC`, reject it when `os.SameFile` matches
the source, and truncate only after that check.

S3. **`Close` reads `wr.end` without the lock** — `image/vhdx/writer.go:446` [Gemini 3.5 Flash]

```go
	if wr.truncate == nil && wr.end < wr.next {
```

`WriteAt` updates `wr.end` under `wr.mu` (line 367), but `Close` reads it after
releasing the lock. The race detector reports it when `Close` overlaps
in-flight writes to a target without `Truncate`, and stays silent for an
`*os.File`, where the short-circuit skips the read. `wr.blocks` and `wr.next`
do not race: every allocation checks `wr.closed` under the same lock, so none
can follow `Close`'s critical section. The doc requires `Close` after all
writes, so only a caller that breaks that rule reaches this.

Fix: read `wr.end` inside the critical section at the top of `Close`.

S4. **The `crypto/rand.Read` error path cannot fire** — `image/vhdx/writer.go:138-140` [Claude Opus 5]

```go
	if _, err := rand.Read(g[:]); err != nil {
		return g, err
	}
```

Since Go 1.24, the module's floor, `crypto/rand.Read` "never returns an error,
and always fills b entirely" (`go doc crypto/rand.Read`) and crashes the
program instead of failing. This check and the three in `NewWriter`
(lines 301-310) are dead code.

Fix: return a bare `guid` from `newRandomGUID` and assign the three GUIDs
directly; with that change, `go vet`, golangci-lint 2.13.2 and the vhdx tests
pass.

S5. **The README offers a raw file as a target without the sizing step** — `README.md:18` [Claude Opus 5]

```markdown
skipping unallocated and zero extents. The target can be a raw file, or a
```

`Convert` skips zero ranges, so a raw target reaches the image size only if
the caller extends it first, as the CLI does at `convert.go:103`. Claude
converted a 64 MiB qcow2 holding one 64 KiB cluster into a fresh file and got a
1,114,112-byte result with no error. `vhdx.Writer` sizes its own file, so the
VHDX recipe needs no such step.

Fix: tell readers to call `f.Truncate(img.Size())` on a raw target first.

S6. **The metadata buffer size is a magic number** — `image/vhdx/writer.go:545` [Claude Opus 5]

```go

```

The 40 is the sum of the item lengths at lines 527-542 (8+8+16+4+4), and
nothing ties the two together; an item added without updating it panics at
line 559 on the first `NewWriter` call.

Fix: size the buffer by summing `item.length` over `items`.

## Design Observations

**Concerns**

- **`Close` finalizes whatever was written** (future) [Codex GPT 5.6 Sol] —
  writing the file type identifier last protects an interrupted conversion
  only while nothing calls `Close`, and a deferred `Close`, the usual Go idiom,
  finalizes a failed one (I1). An explicit finalize step, with `Close` only
  releasing resources, would make the safe path the easy one.
- **The CLI's target setup is not transactional** (future) [Codex GPT 5.6 Sol]
  — validation, truncation, conversion and finalization are spread through
  `cmdConvert`. Converting into a temporary file beside the target and renaming
  it on success would cover I2, S2 and a failure mid-conversion in one change.

**Strengths**

- **Unwritten blocks get `PAYLOAD_BLOCK_ZERO`** (in-scope) [Claude Opus 5] —
  line 594. MS-VHDX 2.5.1.1 leaves `PAYLOAD_BLOCK_NOT_PRESENT` undefined in a
  dynamic image and requires zeros for `PAYLOAD_BLOCK_ZERO`, so skipping zero
  writes is safe for any reader, not only qemu.
- **The file type identifier goes out last** (in-scope) [Claude Opus 5]
  [Codex GPT 5.6 Sol] — lines 452-454. A conversion that stops early leaves a
  file no reader takes for a VHDX, as the second run in I1's probe shows.
- **Output-format and block-size checks run before `os.Create`** (in-scope)
  [Claude Opus 5] [Codex GPT 5.6 Sol] — an invalid `-O` or `-block-size` leaves
  an existing target intact (run), which resolves Copilot's comment on the
  earlier revision.
- **The zero scan runs outside the mutex** (in-scope) [Claude Opus 5]
  [Codex GPT 5.6 Sol] [Gemini 3.1 Pro] [Gemini 3.5 Flash] — lines 389-402.
  Payload writes proceed in parallel, and the re-check under the lock keeps two
  goroutines from allocating one block (I3 asks for a test of it).

### Executive Summary

The PR implements dynamic VHDX image generation, introducing `vhdx.Writer` for concurrent sparse block allocation and integrating it into the convert command. The VHDX spec-compliant implementation is extremely clean and passes all test suites. However, there is a potential data race on writer fields during concurrent writes and `Close()`, and a non-robust flush condition in `writeBAT()`.

#### Important Issues

##### I1. Data race on writer fields during concurrent writes and `Close()` — `image/vhdx/writer.go:428-435` `(important, gap)`

```go
func (wr *Writer) Close() error {
	wr.mu.Lock()
	if wr.closed {
		wr.mu.Unlock()
		return os.ErrClosed
	}
	wr.closed = true
	wr.mu.Unlock()
```

The fields `wr.blocks`, `wr.end`, and `wr.next` are accessed in `Close()` (lines 446-447) and `writeBAT()` (line 586) without holding the mutex `wr.mu`. Since in-flight concurrent `WriteAt` calls can still be updating these fields, this constitutes a data race. Go's race detector will flag this, and it can theoretically cause corrupt BAT writes or incorrect trailing size calculations.

Fix: Take snapshots of `wr.end` and `wr.next`, and copy the `wr.blocks` slice under the lock at the start of `Close()`, then pass the snapshotted values and copied slice to downstream operations.

##### S1. Robust buffer flush condition in `writeBAT` — `image/vhdx/writer.go:581` `(suggestion, enhancement)`

```go
	emit := func(entry uint64) error {
		buf = binary.LittleEndian.AppendUint64(buf, entry)
		if len(buf) == cap(buf) {
			return flush()
		}
		return nil
	}
```

The condition `len(buf) == cap(buf)` assumes `buf`'s capacity will remain exactly at its initial allocation `miB` (which is a multiple of 8). If the capacity changes or if elements are appended with a different size in the future, Go will reallocate `buf` to a larger capacity (e.g., doubling it). Once `cap(buf)` exceeds `miB` and `len(buf)` is not equal to `cap(buf)`, the buffer will never flush and will grow unboundedly.

Fix: Check `len(buf) >= miB` to guarantee a flush at the boundary.

```diff
-		if len(buf) == cap(buf) {
+		if len(buf) >= miB {
```

## Executive Summary

PR #69 adds optional direct-I/O writes to the `convert` package by refactoring the inner goroutine body into a `worker` struct, introducing a `directio` package with platform-specific `Flag` / `DefaultAlignment` constants, and exposing a `-direct` CLI flag. It also factors test helpers into `test/units` and `test/testimage` and adds buffered/direct benchmarks. The core alignment and padding logic is sound — buffer alignment is computed correctly, the last-write padding fires only on the image-end iteration, and worker ownership of mutable state is clean.

Four merge-blockers remain, all addressable with small changes:

1. `directio_other.go`'s build tag is over-broad — `plan9` / `js`-`wasm` / `wasip1`-`wasm` fall into the `O_DSYNC` branch and fail to compile.
2. `Options.Validate()` accepts negative `Alignment`, which then panics inside `allocateBuffer`.
3. The example CLI truncates to `img.Size()` *before* `Convert`; the direct-I/O padding write then extends the file past `img.Size()`, so the on-disk size no longer matches the virtual size.
4. The "extent.Start is cluster-aligned, cluster size divides 4 KiB" invariant that makes the inner `WriteAt` calls safe is load-bearing but not documented or asserted; backends or qcow2 images with sub-4 KiB cluster sizes can silently EINVAL.

I1. **`directio_other.go` build tag covers `plan9`, `js`/`wasm`, and `wasip1`/`wasm`, which lack `syscall.O_DSYNC`** — `directio/directio_other.go:1-13` [Codex GPT 5.5]

```go

//go:build !linux && !freebsd && !netbsd && !dragonfly && !aix && !windows
```

The negation of `directio.go`'s build tag matches every GOOS that is not Linux/FreeBSD/NetBSD/DragonFly/AIX/Windows, including `plan9`, `js`/`wasm`, and `wasip1`/`wasm`. Those targets do not define `syscall.O_DSYNC`, so the new package fails to compile. The library compiled on every other GOOS Codex tried (windows, darwin, freebsd, netbsd, dragonfly, aix, openbsd, solaris, illumos, ios, android, linux/386).

Fix: narrow the O_DSYNC fallback to Unix targets, and add a no-op fallback for non-Unix/non-Windows targets.

```diff

+//go:build unix && !linux && !freebsd && !netbsd && !dragonfly && !aix
```

I3. **Direct-I/O padding extends the destination file past `img.Size()`** — `cmd/go-qcow2reader-example/convert.go:81-99`, `convert/convert.go:291-300` [Gemini 3.1 Pro]

```go
if err := t.Truncate(img.Size()); err != nil {
    return err
}
// ... convert.Convert(t, img, options) follows
```

```go
func (w *worker) ensureAlignment(nr int, extent image.Extent) int {
    if w.opts.Alignment > 0 && extent.Start+extent.Length == w.conv.size && nr%w.opts.Alignment != 0 {
        alignedLen := align.Up(nr, w.opts.Alignment)
        ...
        return alignedLen
    }
    return nr
}
```

The CLI truncates the destination to `img.Size()` *before* `Convert`, but the last padded `WriteAt` writes `alignedLen` bytes starting at an offset that puts the end past `img.Size()`. `pwrite` (and `os.File.WriteAt`) extends the file to cover the write, so the final on-disk size is `align.Up(img.Size(), Alignment)`, not `img.Size()`. A converted raw image should match the virtual size byte-for-byte; this differs from the buffered path and from `qemu-img convert`. The author replied to an earlier reviewer with "We truncate the file at line 81" — that truncate happens before the padded write, so it does not prevent the extension.

Fix: re-truncate to `img.Size()` after `Convert` completes (before `t.Sync()`), so the direct-I/O padding does not leak into the final file size:

```diff
     if err := convert.Convert(t, img, options); err != nil {
         return err
     }
+    if err := t.Truncate(img.Size()); err != nil {
+        return err
+    }
     if err := t.Sync(); err != nil {
         return err
     }
```

I4. **The "extent.Start is `Alignment`-aligned" invariant is load-bearing but undocumented and unchecked** — `convert/convert.go:60-63`, `267-275`, `291-300` [Claude Opus 4.7] [Gemini 3.1 Pro]

```go
// Alignment in bytes for direct I/O. When set, the write buffer is aligned
// to this value and the last write is padded with zeros to the alignment
// boundary. Must be a power of 2, and BufferSize must be a multiple of it.
Alignment int
```

```go
nw, err := w.conv.wa.WriteAt(w.buf[:writeLen], extent.Start)
```

The inner write at line 269 uses `extent.Start` as the file offset, and `ensureAlignment` only pads the last partial read of the *last extent of the image*. Correctness requires every `extent.Start` (from every backend, for every cluster size) to be a multiple of `opts.Alignment`. `image.go:12-14` promises only "Extents are aligned to the underlying file system block size (e.g. 4k), or the image format cluster size (e.g. 64k)" — that holds for typical qcow2 images (64 KiB clusters) but not for qcow2 images created with a 512-byte cluster size, nor for backends whose contract returns sub-`Alignment` extents. Without `O_DIRECT` the write succeeds; with `O_DIRECT` on Linux it returns `EINVAL`.

The author dismissed an earlier reviewer comment with "extent.Start is aligned to cluster size (default 64k), which is aligned to 4k. Check the code returning building the extents." The "default" qualifier hides the assumption.

Fix: tighten the `Alignment` doc comment, and add a defensive check on the first iteration of `copyExtent` that surfaces the misuse instead of letting the kernel fail:

```diff
     // Alignment in bytes for direct I/O. When set, the write buffer is aligned
     // to this value and the last write is padded with zeros to the alignment
-    // boundary. Must be a power of 2, and BufferSize must be a multiple of it.
+    // boundary. Must be a power of 2, and BufferSize must be a multiple of it.
+    // The image backend must also return Extent values whose Start is a multiple
+    // of Alignment. In practice this means Alignment must divide the image's
+    // cluster or block size (typically 64 KiB for qcow2, 4 KiB for raw on
+    // common Linux file systems).
     Alignment int
```

```diff
+    if w.opts.Alignment > 0 && extent.Start%int64(w.opts.Alignment) != 0 {
+        return fmt.Errorf("extent.Start %d not aligned to %d", extent.Start, w.opts.Alignment)
+    }
```

The guard `extent.Start+extent.Length == w.conv.size` is invariant across all iterations of one extent (line 282-283 raises `Start` and lowers `Length` by equal amounts). ## Design Observations

**Concerns**

- **macOS uses `O_DSYNC` rather than `F_NOCACHE`** (in-scope) [Gemini 3.1 Pro] — `directio_other.go` falls back to `syscall.O_DSYNC`, which forces a synchronous flush per write but still routes through the page cache. `qemu-img` bypasses the cache on Darwin via `fcntl(fd, F_NOCACHE, 1)`. The benchmark numbers in the PR description show the `-direct` macOS run still wins handily, so this is not a correctness problem; it is a "the name 'direct' on macOS does not mean what users from a Linux background expect" concern.
- **`Options.Alignment` and the file open flag are coupled but exposed separately** (in-scope) [Claude Opus 4.7] — the example CLI pairs `directio.Flag` and `directio.DefaultAlignment` correctly, but a third-party caller can pass `Options{Alignment: 4096}` while opening the file with neither `O_DIRECT` nor `O_DSYNC` (or vice versa). A single `directio.Options()` helper that returns both, or a doc note that the two must move together, would prevent the mismatch.

**Strengths**

- **Worker / conversion split** (in-scope) [Claude Opus 4.7] [Codex GPT 5.5] — the refactor moves shared conversion state into `conversion` and per-goroutine mutable buffers into `worker`, giving the alignment/padding logic a clear ownership boundary. The inner loop reads better than the deeply nested anonymous goroutine it replaced.
- **`directio` as a thin platform shim** (in-scope) [Codex GPT 5.5] [Gemini 3.1 Pro] — keeping the platform branch in a separate package with just two constants leaves `convert` platform-neutral. The Windows file documents the Go 1.26 TODO precisely.

**Skill improvements**

### Executive Summary

The PR adds optional direct-I/O writes to `convert.Convert` by refactoring the inner goroutine body into a `worker` struct, introducing a new `directio` package with platform-specific `Flag`/`DefaultAlignment` constants, and wiring a `-direct` flag through the example CLI. It also extracts shared test helpers (`test/units`, `test/testimage`) and adds buffered/direct benchmarks. The change is well-structured and the correctness-sensitive code (`allocateBuffer`, `ensureAlignment`) holds up under tracing.

### Findings

#### Critical Issues

None.

#### Important Issues

**I1. Cluster-alignment assumption is load-bearing but undocumented — `convert/convert.go:269, 292`**

```go
nr, err := w.conv.img.ReadAt(w.buf[:n], extent.Start)
...
nw, err := w.conv.wa.WriteAt(w.buf[:writeLen], extent.Start)
```

Direct-I/O writes require the write offset to be aligned to `opts.Alignment`. The code at line 269 writes at `extent.Start` (advanced by `nr` each iteration in line 283). Correctness depends on:

1. The initial `extent.Start` returned by `img.Extent` is aligned to `opts.Alignment`.
2. Every intermediate `nr` is aligned to `opts.Alignment` (so `extent.Start + nr` stays aligned).
3. Only the *final* `nr` of the *last* extent of the image may be unaligned, and that's what `ensureAlignment` handles.

Property 2 holds only because (a) `BufferSize % Alignment == 0` is enforced (line 100), and (b) `ReadAt` is assumed never to return a short read except at EOF (which can only occur at the end of the image). Property 1 holds for qcow2 because cluster size (≥ 64 KiB) is a multiple of 4 KiB, but it is not enforced or even checked for other backends (raw, vmdk, vhdx, vdi, etc.) — the contract in `image/image.go:14` says "Extents are aligned to the underlying file system block size (e.g. 4k), or the image format cluster size (e.g. 64k)" but does not promise alignment to any user-chosen `opts.Alignment`.

The author already addressed this in a PR comment ("extent.Start is aligned to cluster size (default 64k), which is aligned to 4k"), but nothing in the code captures or enforces it. If a future backend returns extents aligned only to 512 bytes, or if a future user sets `Alignment = 8192`, the inner-loop writes would EINVAL on Linux with O_DIRECT — silently passing on macOS where `Flag = O_DSYNC` does not require alignment.

```diff

 	// to this value and the last write is padded with zeros to the alignment
-	// boundary. Must be a power of 2, and BufferSize must be a multiple of it.
```

### Executive Summary

This PR adds direct I/O support to the `convert` package to improve image conversion performance by bypassing the kernel page cache. It introduces an `Alignment` option, refactors the conversion logic into a concurrent worker pool, and adds platform-specific flags. The key findings involve a critical crash when using direct I/O on images with unaligned internal extents, and a gap where the output file's size gets unintentionally inflated by the alignment padding.

### Findings

#### Critical Issues

C1. **Direct I/O fails on images with internal extents unaligned to opts.Alignment** — `convert/convert.go:264-275` (critical, regression)

```go
		for start < end {
			extent, err := w.conv.img.Extent(start, end-start)
			if err != nil {
				return err
			}
			// ...
			} else if err := w.copyExtent(extent); err != nil {
				return err
			}

			start += extent.Length
		}
```

When `O_DIRECT` is enabled, both the buffer and the file offset passed to `WriteAt` must be aligned to the filesystem block size (typically 4096 bytes). While `SegmentSize` and `BufferSize` are properly aligned, the code incorrectly assumes internal extent lengths are also multiples of `opts.Alignment`. If the image format returns an extent with a non-4K length (e.g., a VMDK with 512-byte grains, a qcow2 image with 512-byte clusters, or a raw image with an unaligned sparse hole), `copyExtent` caps the read to this unaligned length. Since it is an internal extent, `ensureAlignment` does not pad it, and `WriteAt` is issued with an unaligned length, failing with `EINVAL`. Furthermore, `start += extent.Length` makes the start offset of the *next* extent unaligned, causing subsequent writes to also fail.

*Note: The author previously dismissed a Copilot comment by stating "extent.Start is aligned to cluster size (default 64k), which is aligned to 4k". This rationale is incorrect because `qcow2reader` supports multiple image formats (like VMDK) and custom qcow2 configurations where clusters/grains are 512 bytes. Therefore, the 4K alignment assumption does not hold universally.*

Fix: When `opts.Alignment > 0`, the worker must decouple I/O chunks from the internal extent boundaries. It should process the image in fixed `BufferSize` blocks and coalesce unallocated extents (holes) smaller than `opts.Alignment` as zeroes to ensure all `WriteAt` calls remain strictly aligned in both length and offset.

#### Important Issues

I1. **Initial Truncate does not prevent file extension from padded writes** — `cmd/go-qcow2reader-example/convert.go:81-83` (important, gap)

```go
	if err := t.Truncate(img.Size()); err != nil {
		return err
	}
	// ... followed by convert.Convert(t, img, options)
```

If an image's virtual size is not a multiple of `opts.Alignment`, `ensureAlignment` pads the final write with zeroes to the alignment boundary. Because POSIX `write()` semantics automatically extend a file when writing past its EOF, this padded write inflates the file size on disk beyond `img.Size()`. A raw image conversion should exactly match the virtual size (like `qemu-img convert` does).

*Note: The author previously dismissed this by pointing to commit `caa0dc7`, which added the `Truncate` call before `Convert` ("We truncate the file at line 81"). This rationale is flawed because truncating the file before conversion does not prevent subsequent padded `WriteAt` calls from extending it again.*

Fix: Move the `t.Truncate(img.Size())` call to execute *after* `convert.Convert` completes (but before `t.Sync()`) to strip the direct I/O padding from the final file.


`Alignment` is an `int`. If a user passes a negative value, it bypasses the validation checks entirely. This will cause `allocateBuffer` to misbehave (e.g., negative length allocation or a panic on `% uintptr(negative)`).

Fix: Change the guard to check for any non-zero value and reject negatives:
```go
	if o.Alignment != 0 {
		if o.Alignment < 0 {
			return errors.New("alignment must be positive")
		}
```

### Design Observations

**Concerns**
- **Emulating O_DIRECT with O_DSYNC on macOS (in-scope)**: In `directio_other.go`, `O_DSYNC` is used as a fallback. `O_DSYNC` does not disable the page cache; it forces a synchronous disk flush on every write, severely degrading performance. `qemu-img` avoids this on macOS by using `fcntl(fd, F_NOCACHE, 1)` to genuinely bypass the page cache. Consider exposing a helper that uses `syscall.Syscall(syscall.SYS_FCNTL, fd, syscall.F_NOCACHE, 1)` on Darwin for true direct I/O emulation.

**Strengths**
- The worker pool design gracefully handles sparse files and zeroes without mutating the destination when not required, which plays perfectly with sparse block backends.
- The separation of platform-specific flags into `directio_*` with build tags is clean and properly isolates the missing `FILE_FLAG_NO_BUFFERING` support on Windows until Go 1.26.

### Testing Assessment

1. **Unaligned image virtual size**: There is no benchmark or test covering the conversion of an image whose virtual size is not a multiple of `opts.Alignment` (e.g., 1000000 bytes). This scenario would trigger the end-of-image padding logic and expose the file-extension bug (I1).
2. **Unaligned internal extents**: There are no tests using `-direct` with an image containing unaligned internal allocations (e.g., a VMDK with 512-byte grains). This would expose the `EINVAL` crash documented in C1.

### Documentation Assessment

The `Convert` method documentation adequately explains the requirements for the destination file and the padding behavior introduced by `Alignment`. No major gaps found.

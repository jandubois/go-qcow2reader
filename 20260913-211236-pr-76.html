At 2^63 or more, int64(offset) is negative. NewSectionReader treats n = -1 as unbounded by setting its limit to MaxInt64, so Read computes limit - off, which overflows to a negative length and slices p[0:-6]. Open loads snapshots eagerly, so any caller that opens such an image crashes, even one that only reads data. The merge-base has no snapshot parsing, so this is new.

The unbounded reader also lets a table grow to about 8.7 GB (65,536 entries of up to 132,136 bytes, computed), where QEMU rejects anything over 64 MiB (QCOW_MAX_SNAPSHOTS_SIZE, checked in block/qcow2-snapshot.c). Claude measured 1.33 GB peak RSS for a 1-byte read of an image with a 1 GiB table. The 2^62 offset and the 1023-entry table are the controls.

// craft returns a v3 qcow2 header with a one-entry L1 table and the given
// snapshot fields, padded to 4 KiB and followed by table.
func craft(nbSnapshots uint32, snapshotsOffset uint64, table []byte) []byte {
	buf := make([]byte, 4096, 4096+len(table))
	copy(buf[0:4], qcow2.Magic)
	binary.BigEndian.PutUint32(buf[4:8], 3)       // version
	binary.BigEndian.PutUint32(buf[20:24], 16)    // cluster bits
	binary.BigEndian.PutUint64(buf[24:32], 65536) // virtual size
	binary.BigEndian.PutUint32(buf[36:40], 1)     // L1 size
	binary.BigEndian.PutUint64(buf[40:48], 512)   // L1 table offset
	binary.BigEndian.PutUint32(buf[60:64], nbSnapshots)
	binary.BigEndian.PutUint64(buf[64:72], snapshotsOffset)
	binary.BigEndian.PutUint32(buf[100:104], 104) // header length
	return append(buf, table...)
}

Design Observations ¶

Concerns ¶

  • The qcow2-specific result has no error path (in-scope) Codex GPT 5.6 Sol Claude Opus 5. The Snapshots() doc comment (image/qcow2/qcow2.go:703-705) sends qcow2 callers to the exported SnapshotEntries field, which is nil when the table failed to load, while the error is in the unexported errSnapshots (line 539). Such a caller cannot tell a broken table from an image without snapshots. A method returning ([]qcow2.Snapshot, error) over unexported storage would keep the result and the error together.
  • Eager parsing ties every command to the table's health (future) Claude Opus 5. With nb_snapshots set to 1 and a zero offset, I confirmed that read now prints WARNING: Failed to read snapshots: invalid snapshot table offset: 0, and snapshot prints the same error twice, as a WARNING from Open and again as an ERROR. Parsing on the first Snapshots() call through sync.Once would spare callers that only read data, at the cost of SnapshotEntries no longer being a plain field.
  • readL1Table has no size cap either (future) Claude Opus 5. It allocates L1Size entries straight from the header (image/qcow2/qcow2.go:454), where QEMU refuses an active L1 table over 32 MiB (QCOW_MAX_L1_SIZE in block/qcow2.h). This predates the PR; a cap there would follow the same pattern as I2's fix.
  • The example commands close the image file twice (future) Gemini 3.1 Pro Gemini 3.5 Flash. Each command defers f.Close() and then img.Close(), which closes the same *os.File, and both errors are ignored (convert.go:58, info.go:46, map.go:51, read.go:56 and snapshot.go:51 in cmd/go-qcow2reader-example/). The new command follows its siblings, so a change belongs in one pass over all five, and a reviewer should not ask this PR to diverge from them.

Review Process Notes ¶

Skill improvements

  • Header fields that place or size a read. When a change parses a binary format from input it did not produce (a disk image, an archive, a network frame), follow every header field that becomes an offset, a length or a count through each type conversion, multiplication and allocation. Flag an unsigned field converted to a signed type with no range check, a count multiplied in a narrower type, and an allocation sized from a field before the bytes behind it are read. When the code cites a reference implementation's limits, read that implementation's validation of the same structure and list every limit it enforces, because a port that copies some limits usually drops others.
  • New work inside an existing guard. When a change adds loading or computation inside an existing guard block (if readable, if enabled, if err == nil), ask whether the new work needs the guard's condition. Enumerate the inputs the guard excludes and check what the new accessor returns for each. A guard the feature does not need switches it off for those inputs, and an accessor that then returns an empty result with no error gives callers a wrong answer they cannot tell from a real one.

Repo context updates

  • Open gates loading on Header.Readable(). qcow2.Open loads the header extensions, the L1 table, the decompressor and the backing file only when Header.Readable() passes, and that check rejects encrypted images, unknown incompatible feature bits and compression types with no registered decompressor. The library registers only zlib, so a zstd image is unreadable to a caller that never calls qcow2.SetDecompressor, while the example CLI registers zstd and reads it. When a change adds metadata loading to Open, check whether the metadata needs decompression or decryption. Metadata that needs neither but loads inside the gate comes back empty for those images, and a test that goes through the CLI cannot show it.
  • io.NewSectionReader(ra, off, -1) needs a non-negative offset. The qcow2 reader uses -1 as its idiom for an unbounded section (the header and the header extensions). With a negative off, the first Read computes a negative length and panics, and converting a uint64 header offset at or above 2^63 to int64 produces exactly that. Flag the idiom wherever the offset comes from a header field, and bound the reader or range-check the offset.
  • Severity baseline for hostile headers. The qcow2 reader does not enforce QEMU's size caps. readL1Table, for one, sizes its allocation from the header's L1 size unchecked. Rate a new unbounded allocation from a header field as a Suggestion against that baseline, and a panic reachable from Open as Important, since it crashes callers that only read data.

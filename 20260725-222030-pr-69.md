## Critical Issues

C1. **`Extent` cannot clip its first cluster, so `Convert` silently drops data** — `image/qcow2/qcow2.go:1050` [Gemini 3.5 Flash] [Claude Opus 5]

```go
		// First cluster: if start is not aligned to cluster size, clip the start.
		if clusterStatus.Start < start {
			clusterStatus.Start = start
			clusterStatus.Length -= start - clusterStatus.Start
		}
```

Line 1049 assigns `clusterStatus.Start = start` before line 1050 reads it, so
the subtraction is always zero. The extent keeps a full cluster's length while
its start moves forward, overhanging into the next cluster, which may have a
different status.

`Convert` reaches this whenever a segment boundary lands mid-cluster.
`Validate` allows that, requiring only `SegmentSize % BufferSize == 0`, so a
legal 96 KiB `SegmentSize` is not a multiple of the 64 KiB cluster size. On a
1 MiB image with cluster 1 unallocated and cluster 2 holding data,
`Extent(98304, 98304)` returns `{Start: 98304, Length: 65536, Zero: true}`,
covering 32 KiB of real data. `Convert` skips the extent and the output loses
32768 bytes with no error.

This predates the PR (commit `5864483`), and the default 32 MiB `SegmentSize`
is cluster-aligned, so no shipped configuration hits it. Fix it separately.

Fix:

```diff
 		if clusterStatus.Start < start {
+			clipped := start - clusterStatus.Start
 			clusterStatus.Start = start
-			clusterStatus.Length -= start - clusterStatus.Start
+			clusterStatus.Length -= clipped
 		}
```

## Important Issues

I1. **Bare-negation build tag breaks compilation on plan9 and both wasm targets** — `directio/directio_other.go:2` [Codex GPT 5.6 Sol] [Claude Opus 5] [Gemini 3.1 Pro] [Gemini 3.5 Flash]

```go

//go:build !linux && !freebsd && !netbsd && !dragonfly && !aix && !windows

package directio

import "syscall"
```

The negation matches every GOOS outside the listed six, including `plan9`,
`js/wasm`, and `wasip1/wasm`, none of which define `syscall.O_DSYNC`. I
confirmed this is a regression rather than a pre-existing gap: `go build ./...`
succeeds for all three targets at merge-base `a6cb46d` and fails at the review
SHA with `directio/directio_other.go:10:22: undefined: syscall.O_DSYNC`.
`solaris`, `illumos`, `openbsd`, `darwin`, `windows`, and `aix/ppc64` all still
build. The author has acknowledged this and named the intended shape (unix,
windows, neither).

Fix: constrain the O_DSYNC file to `unix` and add a no-op file for the rest.

```diff
-//go:build !linux && !freebsd && !netbsd && !dragonfly && !aix && !windows
+//go:build unix && !linux && !freebsd && !netbsd && !dragonfly && !aix
```

I2. **Negative `Alignment` passes validation and panics in a worker goroutine** — `convert/convert.go:96` [Codex GPT 5.6 Sol] [Gemini 3.1 Pro] [Gemini 3.5 Flash] [Claude Opus 5]

```go
	if o.Alignment > 0 {
		if o.Alignment&(o.Alignment-1) != 0 {
			return errors.New("alignment must be a power of 2")
		}
		if o.BufferSize%o.Alignment != 0 {
			return errors.New("buffer size not aligned to alignment")
		}
	}
```

`SegmentSize`, `BufferSize`, and `Workers` each reject negatives explicitly;
`Alignment` does not. `Options{Alignment: -1}.Validate()` returns nil, and
`Convert` then panics at `convert.go:161` with `slice bounds out of range
[-50919773306881:]`. The panic happens inside a worker goroutine, so a caller
cannot recover from it: a bad option value takes down the whole process rather
than returning an error. The author already agreed to add this check.

Fix: reject negatives before the power-of-2 test.

```diff
+	if o.Alignment < 0 {
+		return errors.New("alignment must not be negative")
+	}
 	if o.Alignment > 0 {
```

I3. **`-direct` emits unaligned writes for qcow2 images with sub-4 KiB clusters** — `convert/convert.go:269` [Claude Opus 5]

```go
		if !bytes.Equal(w.buf[:nr], w.conv.zero[:nr]) {
			writeLen := w.ensureAlignment(nr, extent)
			nw, err := w.conv.wa.WriteAt(w.buf[:writeLen], extent.Start)
```

Every write except the image's last one takes its offset and length straight
from the source extent, so both must already be multiples of `Alignment`. The
qcow2 format permits a 512-byte cluster size and `qemu-img create -o
cluster_size=512` produces it. Against such an image, `Convert` with
`Alignment: 4096` issued `WriteAt(off=8704, len=512)`, where both values leave
a remainder of 512. Under Linux `O_DIRECT` on a 4096-byte logical block device
that fails `EINVAL`, so `-direct` cannot convert this input class at all. The
same image converts cleanly with the default 64 KiB cluster size. This is round
1's I4 with a reproduction and the write-length dimension the author's reply
did not cover.

Fix: check the precondition where it is knowable and name the cause.

```diff
 			writeLen := w.ensureAlignment(nr, extent)
+			if w.opts.Alignment > 0 && (extent.Start%int64(w.opts.Alignment) != 0 ||
+				writeLen%w.opts.Alignment != 0) {
+				return fmt.Errorf("unaligned write at %d (%d bytes): image granularity "+
+					"is smaller than alignment %d", extent.Start, writeLen, w.opts.Alignment)
+			}
```

I4. **Buffered and direct benchmarks stop at different durability boundaries** — `convert/convert_test.go:246` [Claude Opus 5] [Codex GPT 5.6 Sol]

```go
	if err := Convert(dst, img, opts); err != nil {
		b.Fatal(err)
	}
	if err := dst.Close(); err != nil {
		b.Fatal(err)
	}
```

`close(2)` does not flush dirty pages. The buffered sub-benchmarks stop the
timer with up to 2 GiB still in the page cache, while the direct arm has
already waited for the device under `O_DIRECT` or `O_DSYNC`. The two arms
therefore measure different guarantees, and the deferred writeback lands inside
a later `b.N` iteration and inflates it. The bias runs against the PR's own
claim, so the published numbers are not overstated; they come from the CLI,
which does call `Sync` at `cmd/go-qcow2reader-example/convert.go:94`. Still,
these benchmarks are the committed artifact for reproducing that claim.

Fix:

```diff
 	if err := Convert(dst, img, opts); err != nil {
 		b.Fatal(err)
 	}
+	if err := dst.Sync(); err != nil {
+		b.Fatal(err)
+	}
 	if err := dst.Close(); err != nil {
```

## Suggestions

S1. **No test exercises a `Convert` call with `Alignment` set** — `convert/convert_test.go:63` [Codex GPT 5.6 Sol] [Claude Opus 5] [Gemini 3.1 Pro] [Gemini 3.5 Flash]

`TestAllocateBufferAligned` covers the buffer address and `TestValidateAlignment*`
covers option parsing. Nothing calls `Convert` with `Alignment > 0` outside the
benchmarks, and CI runs `go test -v ./...` without `-bench`, so the entire
`ensureAlignment` branch is unreached by the test suite. A fake `image.Image`
of, say, 100 bytes plus a recording `io.WriterAt` covers the padding path, the
write offsets, and the progress total in one test with no `qemu-img`
dependency. The author has listed this as a known gap. Round 1 raised it as S1
and nothing has changed.

S2. **The padding guard is broader than the case it means to catch** — `convert/convert.go:292` [Gemini 3.1 Pro]

```go
	if w.opts.Alignment > 0 && extent.Start+extent.Length == w.conv.size && nr%w.opts.Alignment != 0 {
```

`extent.Start+extent.Length` is invariant across the chunk loop, so this is
true for every chunk of an extent that reaches the image end, not only the
final one. Today that is harmless: `BufferSize % Alignment == 0`, so a full
chunk always has `nr % Alignment == 0` and falls through. The guard therefore
depends on a caller-supplied invariant to express "this is the last write."
With a source whose `ReadAt` returns a short count and a nil error, I measured
3904 stray zero bytes written into the middle of the output and a file 3904
bytes too long. Both in-repo `ReadAt` implementations conform, so no shipped
backend triggers it.

Fix, which also removes the need for round 1's S4 comment:

```diff
-	if w.opts.Alignment > 0 && extent.Start+extent.Length == w.conv.size && nr%w.opts.Alignment != 0 {
+	if w.opts.Alignment > 0 && extent.Start+int64(nr) == w.conv.size && nr%w.opts.Alignment != 0 {
```

S3. **Document that `-direct` rounds the output size up** — `cmd/go-qcow2reader-example/convert.go:81` [Gemini 3.1 Pro] [Claude Opus 5]

```go
	if err := t.Truncate(img.Size()); err != nil {
		return err
	}
```

This truncate runs before `Convert`, and the padded last write then extends the
file past `img.Size()`. Converting a 100-byte image with `Alignment: 4096`
produced 4096 bytes; 12281 bytes produced 12288. Round 1 called this a
merge-blocker on the grounds that it differs from `qemu-img convert`, and that
comparison was against buffered `qemu-img`. Measured with qemu-img 11.0.2 on a
qcow2 whose virtual size is 12288: `qemu-img convert -O raw` writes 12288
bytes, and `qemu-img convert -O raw -t none -W` writes 16384. QEMU's own direct
mode pads exactly the way this PR does, so the author's position holds and the
finding is now a documentation gap: neither `Options.Alignment` nor the
`-direct` flag help says the output grows.

S4. **The new `-direct` CI step cannot reach the padding path and breaks on the first unaligned image** — `hack/compare-with-qemu-img.sh:80` [Claude Opus 5] [Gemini 3.1 Pro]

```bash
if [ "${expected}" = "${got}" ]; then
```

The step hashes the whole `-direct` output and compares it against buffered
`qemu-img` output. All four CI images are 2 GiB and 4 GiB with 64 KiB clusters,
so `nr % Alignment != 0` never holds and this step asserts nothing the buffered
step at lines 67-76 does not. Add an image whose virtual size is not a multiple
of 4096 and the step turns red for behavior S3 shows is intended. The script
and the design disagree.

Fix: hash only the first `img.Size()` bytes of `raw_d`, then add an unaligned
image so the padding path is covered.

S5. **Destination permissions no longer honor the umask** — `cmd/go-qcow2reader-example/convert.go:75` [Codex GPT 5.6 Sol]

```go
	t, err := os.OpenFile(target, openFlags, 0644)
```

The merge base called `os.Create(target)`, which requests 0666 and lets the
umask subtract. Adding `openFlags` required the explicit mode, and 0644 drops
group write for everyone regardless of their umask. Building both revisions and
running each under `umask 0002` produced 664 for the merge base and 644 for
HEAD. Unrelated to direct I/O and invisible in the diff unless you know what
`os.Create` passes.

```diff
-	t, err := os.OpenFile(target, openFlags, 0644)
+	t, err := os.OpenFile(target, openFlags, 0666)
```

S6. **`-direct` is a silent no-op on Windows** — `cmd/go-qcow2reader-example/convert.go:70` [Claude Opus 5]

```go
	if direct {
		openFlags |= directio.Flag
		options.Alignment = directio.DefaultAlignment
	}
```

`directio.Flag` and `DefaultAlignment` are both 0 on Windows, so the flag is
accepted and does nothing. A user comparing timings there sees buffered numbers
labeled direct. One line on stderr when `directio.Flag == 0` makes the
documented limitation visible at the point it bites. Round 1 raised this as S3.

S7. **`testimage.Create` writes past the requested size** — `test/testimage/testimage.go:84` [Gemini 3.5 Flash]

```go
			chunk := io.LimitReader(reader, dataSize)
```

When `size % chunkSize != 0`, the final iteration copies a full `dataSize`
chunk starting at `offset`, extending the file past the `Truncate(size)` above.
Every current caller passes a multiple of 8 MiB, so nothing fires today. The
bug came through unchanged from the extracted helper, so it predates this PR.
Capping the limit at `size - offset` is a two-line fix. Round 1 raised this as
S2.

S8. **Benchmark timer covers open, parse, and a 2 GiB truncate** — `convert/convert_test.go:222` [Claude Opus 5] [Codex GPT 5.6 Sol] [Gemini 3.5 Flash]

`benchmarkConvert` starts the timer before `os.Open`, `qcow2reader.Open`,
`os.OpenFile`, and `dst.Truncate(img.Size())`. Commit `caa0dc7` added that
truncate inside the timed region. Moving `b.StartTimer()` to just before
`Convert` and `b.StopTimer()` to just after makes the numbers measure the thing
the benchmark is named for. Round 1 raised this as S5.

S9. **`Validate` boundary cases go untested** — `convert/convert_test.go:29` [Claude Opus 5]

Worth adding, all mechanical: `Alignment: -1` (I2), `Alignment: 4096` with
`BufferSize: 1024`, and an assertion in `TestValidateAlignment` that
`opts.BufferSize % alignment == 0` after `Validate()` fills in the defaults.
That last one pins the relationship I2's fix and S2's argument both rest on.
Round 1 raised these as S6 and S7.

S10. **Record why slicing to an aligned address is safe** — `convert/convert.go:158` [Claude Opus 5]

```go
	buf := make([]byte, opts.BufferSize+opts.Alignment)
	remainder := int(uintptr(unsafe.Pointer(&buf[0])) % uintptr(opts.Alignment))
```

This is the standard Go direct-I/O idiom and it is correct, because the garbage
collector does not relocate heap objects and `buf` keeps the allocation alive.
The `unsafe.Pointer` to `uintptr` conversion is also the one direction `go
vet`'s `unsafeptr` check does not police, so nothing would flag it if the
assumption changed. One sentence on `allocateBuffer` tells the next reader the
question was asked and answered.

S11. **A `test:` commit introduces the public `directio` package** — commit `306dba9` [Claude Opus 5]

`306dba9 test: Add direct I/O benchmarks for convert package` adds
`directio/directio.go`, `directio/directio_other.go`, and
`directio/directio_windows.go` alongside the benchmark changes. Those three
files are a new exported package of the module, which the subject hides from
anyone scanning history for API additions or bisecting a build break on an
esoteric platform. Splitting them into a `directio:` commit ordered before the
benchmarks that consume them costs one rebase.

S12. **Four typos in `convert/convert.go` comments** — `convert/convert.go:40` [Gemini 3.5 Flash] [Claude Opus 5]

## Design Observations

**Concerns**

- **The direct-I/O contract has three owners and one enforcement point**
  (in-scope) [Claude Opus 5] [Codex GPT 5.6 Sol] [Gemini 3.5 Flash] — a working
  `-direct` conversion needs an aligned buffer address (owned by
  `allocateBuffer`), aligned write offsets and lengths (owned by the source
  image's extent granularity), and the right open flag on the destination
  (owned by the caller). Only the first is checked. I3 turns the second into a
  diagnosable error; a `directio.Open` helper returning both the file and the
  matching `Options.Alignment` would close the third. The richer option is a
  read-modify-write path for sub-alignment fragments, which would let `-direct`
  handle small-cluster images instead of failing cleanly on them.
- **"Direct" means something different on macOS** (in-scope) [Gemini 3.1 Pro]
  [Codex GPT 5.6 Sol] [Gemini 3.5 Flash] — `O_DSYNC` makes each write
  synchronous but still routes through the page cache, where `qemu-img` uses
  `fcntl(fd, F_NOCACHE, 1)` on Darwin. The measured speedup is real, so this is
  about the name matching the behavior, either by switching to `F_NOCACHE` or
  by saying what the flag does per platform.
- **No negotiation with filesystems that reject `O_DIRECT`** (future)
  [Codex GPT 5.6 Sol] — the author raised this himself: Linux tmpfs rejects
  `O_DIRECT`, so making this the default in `limactl` would break users whose
  lima home sits on tmpfs. Opening with `O_DIRECT` and falling back on `EINVAL`
  is the usual shape. Worth settling before any caller turns it on by default.
- **Pre-existing: a zero-length extent would hang `Convert`** (future)
  [Claude Opus 5] — `convert/convert.go:229` advances `start` by
  `extent.Length`, so a backend returning a zero-length extent with a nil error
  spins forever inside `run` rather than failing. No in-repo backend does this,
  and the merge-base code had the same shape.

**Strengths**

- **The worker extraction earns its place** (in-scope) [Claude Opus 5]
  [Codex GPT 5.6 Sol] [Gemini 3.5 Flash] — six `setError`-and-`return` sites
  collapse into plain `return err`, and `zeroExtent` / `copyExtent` /
  `ensureAlignment` name the three cases the old nested closure left implicit.
  I diffed the new loop against the deleted one: it is faithful, including the
  subtlety that `copyExtent` takes its extent by value so the caller's
  `start += extent.Length` still advances by the original length.
- **`Alignment == 0` preserves the old path exactly** (in-scope)
  [Claude Opus 5] — `allocateBuffer` returns a plain `make`, and
  `ensureAlignment` short-circuits on its first conjunct. Existing callers see
  no change.
- **`directio.go` records how its platform list was derived** (in-scope)
  [Claude Opus 5] — the header comment names the check (`O_DIRECT` in
  `zerrors_*_*.go`), which let reviewers verify the list mechanically instead
  of guessing. The list is correct; only its negation is wrong.

## Testing Assessment

I ran the suite myself at the review SHA on darwin/arm64 with `qemu-img` and
`qemu-io` 11.0.2 on PATH: `go test ./...` passes for every package,
`golangci-lint run` (v2.12.2) reports 0 issues, and `go vet ./...` is clean.
Agent worktrees produced the same result, and Codex additionally ran
`go test -race` and drove `hack/compare-with-qemu-img.sh` against a 1 MiB
image. Nothing here reaches real Linux `O_DIRECT`; every claim about `EINVAL`
rests on the alignment of the write arguments, which I did measure.

Gaps, by risk:

1. **Any `Convert` call with `Alignment > 0`.** CI never runs it (S1). The
   padding branch, the write offsets under alignment, and the progress total
   are all uncovered.
2. **The padding path itself.** Every CI image has a GiB-sized virtual size, so
   `nr % Alignment != 0` never holds, including in the new `-direct` script
   step (S4). One image with an unaligned virtual size covers S3 and S4 at once.
3. **Non-default cluster sizes with `Alignment` set.** The I3 reproduction took
   two `qemu-img`/`qemu-io` calls and a recording `io.WriterAt`; a permanent
   regression test costs about the same.
4. **Cross-GOOS build coverage.** I1 has now escaped two rounds because no job
   builds for the targets on the negated branch of the tag.
5. **Error paths.** Short reads, EOF with data, short writes, and a failing
   worker are untested, including whether the first error is the one returned
   and whether progress stops.
6. **Filesystems that reject `O_DIRECT`,** and Windows, where `-direct` does
   nothing at all.

## Documentation Assessment

- `Options.Alignment` (`convert/convert.go:60`) states the power-of-2 and
  `BufferSize` constraints. It omits the two that bite: the destination must be
  opened with `directio.Flag`, and the source's extent granularity must be at
  least `Alignment` (I3).
- The `Convert` doc comment (`convert/convert.go:166`) describes the sparse
  target contract but not that `Alignment` can round the output size up (S3).
- The `-direct` flag help says "use direct I/O for writing" with no mention
  that it is synchronous rather than uncached on macOS and inert on Windows.
- `ensureAlignment` (`convert/convert.go:288`) understates its safety argument.
  Fixing the guard per S2 removes the need for the comment entirely.
- `directio` has no package doc comment. Neither do `align`, `convert`, or
  `lru`, so this matches the repo and is not worth changing on its own.
- `test/units/units.go` exports three constants with no doc comments.

## Acknowledged Limitations

- **Author states the PR is unfinished** ([2026-07-23 comment](https://github.com/lima-vm/go-qcow2reader/pull/69#issuecomment-5062379147)):
  "build is still not entirely correct on esoteric platforms, should be more
  precise (unix, windows, not unix or windows"; "new code to handle the final
  unaligned write has not tests"; and tmpfs on Linux rejects `O_DIRECT`. Those
  map to I1, S1, and the filesystem-negotiation concern. The verdict follows
  the author's own assessment.
- **Padded writes grow the output** — declined Round 1: the author holds that
  disk images emulate block devices and QEMU behaves the same way. Measurement
  supports him (S3), so this round asks only for documentation.
- **`extent.Start` is cluster-aligned in practice** — the author's reply is
  accurate for the default 64 KiB cluster size. I3 shows the non-default case
  and the write-length dimension the reply does not cover.
- **Deferred plus explicit `Close`** — declined Round 1: "The second close is
  harmless and error checking is not needed. The double close ensures that the
  file is close on all errors, and that we respect an error from the close."
  Not re-raised.
- **Windows direct I/O postponed** — `directio/directio_windows.go:2` documents
  that `syscall.Open` passes `FILE_FLAG_NO_BUFFERING` only from Go 1.26, and
  `go.mod` declares 1.24. S6 asks for a warning, not for the feature.
- **`zeroExtent` punches no holes** — `convert/convert.go:234` notes this and
  relies on the documented new-or-zeroed destination. Unchanged by this PR.
- **Raw images report one all-allocated extent** — `image/raw/raw.go:26` has
  SEEK_HOLE/SEEK_DATA as a TODO. Harmless for alignment, since segment
  boundaries are `BufferSize` multiples.

## Review Process Notes

**Skill improvements**

- **Forbid editing the code under review.** The worktree rule currently bars
  branches and commits and points scratch work at `.scratch/`, which leaves
  editing tracked files allowed by omission. Add: "Do not modify any tracked
  file in the working tree. To test a hypothesis that needs a code change,
  describe the change and the expected result in the finding instead of
  applying it. Any test or build you run must run against the unmodified
  tree." A reviewer that patches the tree and then runs the suite is reviewing
  its own edit, and every coverage and test claim it makes afterwards
  describes code the author never wrote.
- **Check that a benchmark's arms stop at the same completion boundary.**
  When a change ships benchmarks comparing two I/O or concurrency modes,
  verify both arms wait for the same guarantee before the timer stops: the
  same flush, the same durability barrier, the same cache state. Look for a
  shared helper that closes or returns without syncing while one mode's flag
  or option makes its writes synchronous. An arm that stops earlier is not
  slower or faster, it is measuring something else, and the deferred work
  usually lands inside the next iteration.
- **Diff the effective defaults when a convenience constructor is replaced by
  its explicit form.** A refactor that needs one extra argument commonly
  rewrites `os.Create(p)` into `os.OpenFile(p, flags, mode)`, or the
  equivalent in other languages, and silently adopts whatever the author typed
  for the arguments the convenience form used to supply. Compare each implied
  argument against the documented default of the call being replaced. These
  changes are invisible in review because the new line looks deliberate and
  the old default is not on screen.

**Repo context updates**

- `[repo]` `convert.Options.Validate` constrains `SegmentSize` only against
  `BufferSize`, never against the source image's cluster size. A caller may
  therefore pass a legal `SegmentSize` that is not a multiple of the cluster
  size, which makes worker segment boundaries land mid-cluster and produces
  `Extent` queries at non-cluster-aligned offsets. When reviewing anything
  that consumes `Extent` results, check whether the query offsets are
  cluster-aligned before trusting the returned status and length, and treat
  a mid-cluster query as an untested path.
- `[repo]` `qemu-img convert -O raw` writes exactly the image's virtual size,
  while `qemu-img convert -O raw -t none -W` rounds the output up to the
  direct-I/O alignment. Comparisons against `qemu-img` output must therefore
  match the caching mode, and a size difference between a direct-mode
  conversion and buffered `qemu-img` output is expected behavior rather than a
  defect. `hack/compare-with-qemu-img.sh` hashes whole files, so it can only
  compare modes that pad identically.

**I1. `-direct` emits unaligned writes for qcow2 images with a small cluster size — `convert/convert.go:269`** *(important, regression)*

```go

`ensureAlignment` (line 292) pads only the write whose extent ends at `conv.size`. Every other write inherits its offset and length from the source extents, so both must already be alignment-multiples. ## Design Observations

### Concerns

- **The direct-I/O contract is enforced nowhere it can be checked (in-scope).** `Convert` requires three properties that are produced by three different owners: the buffer address (owned by `allocateBuffer`), the write offset and length (owned by the image backend's extent granularity), and the file open flag (owned by the caller). Only the first is enforced. A small contract check inside `copyExtent` — the guard sketched in I1 — makes the invariant explicit and turns a device-dependent `EINVAL` into a message naming the actual cause. A larger option is to let `Convert` fall back to a read-modify-write for any sub-alignment fragment, which would also make `-direct` work on small-cluster images rather than merely failing clearly.
- **Pre-existing, surfaced while tracing the alignment argument.** `image/qcow2/qcow2.go:1048-1051` cannot clip the first cluster: line 1049 assigns `clusterStatus.Start = start` before line 1050 computes `start - clusterStatus.Start`, so the subtraction is always zero and the extent's length overhangs its start when `start` is not cluster-aligned. `convert` never triggers it (it always queries at cluster-aligned offsets), but the direct-I/O feature now depends on this function's alignment guarantees, so the latent bug is worth fixing. Separately, `convert/convert.go:217-230` spins forever if a backend ever returns a zero-length extent with a nil error — `start` never advances and `nextSegment` is never reached again, so `Convert` hangs rather than failing. Both predate this PR.

### Strengths

- The `worker` extraction is a genuine readability win: error handling collapses from six `setError`-and-`return` sites into plain `return err`, and `zeroExtent`/`copyExtent`/`ensureAlignment` name the three cases the old nested loop left implicit.
- `Alignment == 0` keeps the previous code path byte-for-byte: `allocateBuffer` returns a plain `make`, and `ensureAlignment` short-circuits on the first conjunct. Existing callers are unaffected.
- The build-tag header in `directio/directio.go:1-4` records *how* the platform list was derived, which let me verify it mechanically against the Go source rather than guess. More comments should do this.

## Testing Assessment

Untested scenarios, highest risk first:

1. **Any `Convert` call with `Alignment != 0`.** No test invokes it; only benchmarks do, and benchmarks do not run in CI (`go test -v ./...`). The entire `ensureAlignment` branch is dead code from CI's perspective.

### Findings

#### Critical Issues

C1. **`ensureAlignment` incorrectly pads intermediate chunks of the last extent** — `convert/convert.go:292-293`

	if w.opts.Alignment > 0 && extent.Start+extent.Length == w.conv.size && nr%w.opts.Alignment != 0 {
```

### Findings

#### Critical Issues

C1. **Incorrect extent length clipping on unaligned queries causes overlapping cluster states** — `image/qcow2/qcow2.go:1046-1051` (critical, gap)

```go
		// First cluster: if start is not aligned to cluster size, clip the start.
		if clusterStatus.Start < start {
			clusterStatus.Start = start
			clusterStatus.Length -= start - clusterStatus.Start
		}
```

When `img.Extent` is queried with an unaligned start offset, `clusterStatus.Start` is updated to `start` on line 1047 first. Consequently, the subtraction `start - clusterStatus.Start` on line 1048 evaluates to `0`, leaving `clusterStatus.Length` untruncated. This causes unaligned queries spanning cluster status boundaries to return incorrect, overlapping lengths. During parallel conversion with unaligned worker segment offsets, this triggers silent target image corruption.

The full call chain path demonstrating this impact:
1. `convert/convert.go:197` — Worker queries `img.Extent` with an unaligned segment offset.
2. `image/qcow2/qcow2.go:1046-1051` — `Extent` fails to clip the length, overlapping status boundaries.
3. `convert/convert.go:217` — `WriteAt` writes unaligned/incorrect sparse blocks, corrupting the target.

Fix: Preserve the original offset difference before modifying `clusterStatus.Start`:

```diff
		// First cluster: if start is not aligned to cluster size, clip the start.
		if clusterStatus.Start < start {
+			diff := start - clusterStatus.Start
			clusterStatus.Start = start
-			clusterStatus.Length -= start - clusterStatus.Start
+			clusterStatus.Length -= diff
		}
```

### Design Observations

**Concerns**
1. **Direct I/O Emulation on macOS via `O_DSYNC`** `(in-scope)` — On macOS, direct I/O is emulated using `O_DSYNC` rather than `fcntl(F_NOCACHE)`. While this matches QEMU's behavior, it means that the writes still go through the page cache and may not achieve true bypass of the OS buffer cache on macOS.
2. **Coupling of `Options.Alignment` and File Open Flags** `(in-scope)` — The file open flags (e.g. `O_DIRECT`) and the alignment option (`Options.Alignment`) are tightly coupled but configured completely separately. A caller can open a file with `O_DIRECT` but forget to set `Options.Alignment` (causing alignment write failures), or set `Options.Alignment` on a buffered file descriptor (adding unnecessary zero-padding and alignment computations).

**Strengths**
1. **Platform-Specific Build Tags** — Splitting direct I/O flag configurations by OS platforms using build tags allows compiling cleanly on major supported targets.
2. **Sequential worker coordination** — Extracted `worker` struct significantly simplifies the `Convert` function's control flow and goroutine logic, improving maintainability.

### Testing Assessment

The following testing gaps were identified:
1. **Direct I/O Unit Tests**: The unit tests for conversion in `convert/convert_test.go` only test validation and buffer allocation. No unit test exercises the actual `Convert` flow with `Alignment > 0` and direct I/O enabled; it is only covered by benchmarks and integration scripts.
2. **Unaligned Start Boundary Queries**: As demonstrated in the new test we added to `TestExtentsSome` (which failed prior to our fix), unaligned queries across cluster boundaries were previously untested and suffered from an active data corruption bug.
3. **Unaligned segment-size conversions**: No test covers converting images with a `SegmentSize` or `BufferSize` unaligned to cluster boundaries, which is critical to verify the correctness of sequential extent chunking.

### Documentation Assessment

1. **Missing documentation of `Options.Alignment` constraints**: The documentation for `Options.Alignment` does not state that `extent.Start` and segment alignment must divide the cluster/block size of the filesystem.
2. **`Updater.Update` typo**: Correct the typo "successfu" on line 39 of `convert/convert.go`.

### Acknowledged Limitations

1. **Double Close on os.File** (`defer file.Close()` + `return file.Close()`) — The double-close pattern is used in `cmd/go-qcow2reader-example/convert.go` and `test/testimage/testimage.go:93`. The author has acknowledged this and clarified that the double-close is harmless and ensures files are closed on all paths while preserving close errors.
2. **Padded Writes Extend the File Past Virtual Size** — With `-direct`, padded writes of the last sector can extend the file beyond `img.Size()`. The author has clarified that this is expected behavior for block devices and matches QEMU.
3. **Missing Windows Direct I/O Support** — Windows direct I/O is emulated as buffered I/O with `Flag = 0` and `DefaultAlignment = 0` because `FILE_FLAG_NO_BUFFERING` is only fully passed to `syscall.Open` from Go 1.26 onwards.

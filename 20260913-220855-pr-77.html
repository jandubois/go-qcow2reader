Executive Summary ¶

The amended commit fixes the ten round-1 findings the author accepted. Two Important findings remain, each a few lines to fix. The CLI still empties an existing target when it cannot read the source (a vmdk, an encrypted qcow2, or a qcow2 whose backing file has moved), the same loss round 1 fixed for invalid options. And WriteAt after Close does not always return the os.ErrClosed its doc promises.

Four reviewers ran against b5b32b0, and all four finished. Claude found I1 and Codex found I2. Each Important finding has a reproducer run from this report, and each patch was run against its reproducer. Codex also found a pre-existing qcow2 bug that silently drops data when the segment size is not a multiple of the cluster size; the PR does not touch that code, so it is under Design Observations. Neither Gemini finding survived verification.

Design Observations ¶

Concerns ¶

  • Unaligned segment sizes silently drop qcow2 data (future) Codex GPT 5.6 Sol — image/qcow2/qcow2.go:1049-1050 sets clusterStatus.Start = start before it subtracts start - clusterStatus.Start, so an extent that starts mid-cluster keeps its full length, and Convert skips a zero extent past the start of the next cluster. On a 512 KiB qcow2 with one 64 KiB cluster of data at 128 KiB, convert -buffer-size=1000 -segment-size=100000 -workers=1 exits 0 and qemu-img compare reports a mismatch at offset 131072, for raw and VHDX output alike; -buffer-size=65536 -segment-size=131072 converts identically. The PR does not touch image/qcow2, and the merge-base CLI already took both flags, so this needs its own issue. Codex's patch (compute the clip before moving the start, and cap the length at remaining) fixed all four option sets I tried and passes the root tests. With only the two lines reordered, the same run did not finish within five minutes. The S1 fix from round 1 makes -segment-size and -buffer-size show up in convert -h for the first time.
  • The CLI's target setup is still not transactional (future) Claude Opus 5 — round 1 raised this. I1 and S1 are two more failures that leave the target empty. Converting into a temporary file beside the target and renaming it on success would cover both, and a failure mid-conversion too. I1 stands as its own finding because its error is known before the target is opened.

Strengths ¶

  • The same-file check compares the open files (in-scope) Claude Opus 5 Codex GPT 5.6 Sol — the target is opened without O_TRUNC and compared with the source through os.SameFile on the two open handles, so no path can change between the check and the truncation. On Windows, Go 1.24 opens every O_CREATE file with OPEN_ALWAYS and truncates afterwards (syscall/syscall_windows.go in the Go 1.24.0 source), so dropping O_TRUNC changes nothing there. A target naming the source by the same path, a symlink or a hard link was refused for raw and VHDX output in my runs, Claude's and Codex's.
  • Every option check runs before the target is opened (in-scope) Codex GPT 5.6 Sol Claude Opus 5 — seven invalid option sets in my run, and eight in Claude's, left an existing target intact.

Acknowledged Limitations ¶

Declined in prior rounds ¶

  • The README example finalizes a failed conversion as a valid VHDX — declined Round 1: no convention requires a failed conversion to leave an invalid image, and raw output cannot enforce one; the maintainer agreed that README samples need not show full error handling. The raw example added this round follows the same style.

Unchanged ¶

  • Round-1 limitations — blocks are never deallocated, the target must be new or zeroed, Close must follow all writes, the log stays empty, and the default block size is small because some file systems fill small holes (image/vhdx/writer.go:62, 169-172, 216-227).
  • The CLI writes only to regular files — Linux's ftruncate(2) returns EINVAL for a file that is not regular, so a block-device target fails at Truncate, as it did at the merge-base; on macOS a /dev/null target fails at fsync on both SHAs. Skipping the truncation for devices would corrupt output, because Convert skips zero ranges and a device holding old data keeps it there. A future reviewer should not suggest skipping Truncate for devices unless the fix also zeroes the device.

Review Process Notes ¶

Skill improvements

  • Checks that gate a destructive step. When a change adds or moves checks ahead of a destructive step (truncating or overwriting an output, deleting a file, dropping a table), list every failure the code can detect from what it already holds at that point, including ones the change does not mention: whether the input can be read, its size, the output's identity. Flag any that still runs after the step, because it fails after the damage is done.
  • Error contracts against early returns. When a doc comment promises an error for a state (closed, cancelled, expired), trace every return that can come before the state check, including the ones empty input and out-of-range arguments take, and flag the doc or the order when one skips the check.

Repo context updates

  • [repo] UPDATE "SegmentSize is unconstrained against cluster size": the qcow2 Extent does not shorten the first extent when a query starts mid-cluster (it overwrites Start before computing the clip), so Convert with a segment size that is not a multiple of the cluster size skips data and exits 0 (measured 2026-09-13 with -buffer-size=1000 -segment-size=100000). Treat an unaligned extent query as broken, not merely untested, until the first-cluster clip in image/qcow2/qcow2.go computes the clip before it moves the start.
  • [repo] The example CLI's convert command truncates an existing target before converting, so every error it can detect without writing (option values, output format, block size, source readability through img.Readable(), a target that is the source or its backing file) belongs before the truncation. When reviewing a change to that command, list the checks on each side of the truncation.
  • [repo] image.Image.Readable has three implementations: qcow2 (a cached header check that also covers a backing file it cannot open), raw (always nil) and image/stub (always an error), which backs vmdk, vdi, vpc, parallels, asif and the vhdx reader. qcow2reader.Open succeeds for all of them, so code that must know whether a source converts calls Readable() instead of trusting Open.
